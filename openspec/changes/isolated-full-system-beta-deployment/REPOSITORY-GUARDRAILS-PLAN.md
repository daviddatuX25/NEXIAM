### G3 — Bring the greenfield checks online

1. Compare the repo-local two-job workflow, the private multi-job candidate, and actual package scripts/lockfiles at the selected baseline. Choose one `.github/workflows/system-quality.yml`; retain legacy coverage separately. Give independent checks stable names and observable outcomes for PHP formatting, PHP tests, frontend types, lint, format, Vitest, production dependency audits and build. 2. Use pinned actions, read-only token permissions and nonpersisted checkout credentials; PRs use disposable data and no production secrets or production deploy jobs. Validate fork behavior and ensure path routing cannot strand a required check in `Expected` or report a green aggregate when a required job failed, was canceled, or was skipped incorrectly. 3. With push/PR approval, open a scoped PR and record the exact head SHA, hosted run URL, job names and results. Use `gh pr checks <pr>` and `gh run view <run-id>` against that SHA. Repair and rerun affected jobs on scoped changes. **Proof:** a green system PR, accounted-for docs-only behavior, and a deliberate red probe with the expected check on a disposable test branch/PR. No masking via `continue-on-error`, skipped suites, lowered thresholds, or hand-edited success. A red baseline is a blocker, not a passing check to require prematurely.
