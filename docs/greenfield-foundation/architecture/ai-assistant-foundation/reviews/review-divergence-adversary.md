# Divergence Adversary Review — AI Assistant Foundation

**Reviewed:** `ARCHITECTURE-SPINE.md` with `READINESS-PLAN.md` as a non-binding companion  
**Method:** Construct two implementation units one level below the spine, require both to obey every current AD, then identify where their shared contracts or behavior can still be incompatible.  
**Initial verdict:** **REVISE.** The direction was coherent and the authority boundary was substantially right, but the original spine was not yet a sufficient build substrate for independent teams.  
**Historical AD-20/AD-21 second-pass verdict:** **REVISE.** The prior five top integration holes were closed, but four build-critical seams remained underdefined.  
**Current verdict after closure review:** **PASS.** AD-7, AD-16, and AD-20–AD-22 now close shared domain-rule execution, proposal evidence binding, atomic rule-change propagation, and enforced knowledge-route dispatch. No high/critical divergence remains in the reviewed seams; exact storage and worker mechanics may proceed to AI-009/OpenSpec without weakening the binding fail-closed contracts.

## Two compliant but incompatible implementation units

| Seam | Unit Atlas — kernel-centric | Unit Beacon — adapter/orchestrator-centric | Why both currently comply |
| --- | --- | --- | --- |
| Registry | Immutable PHP definitions compiled to JSON Schema Draft 2020-12; registry rejects duplicate keys at boot | Database-backed manifests loaded by domain providers; OpenAPI-style schemas and last-provider-wins collision handling | AD-2 requires a versioned definition and schemas but fixes neither representation, dialect, publication, nor collision behavior |
| Dispatch/auth | Kernel owns the ordered pipeline: validate → authorize → scope → execute → project → audit | Capability handlers/decorators own authorization and scope; kernel only looks up, validates, and dispatches | AD-1/AD-2 require authorization and scope metadata but do not assign the enforcement step or order |
| Shared result | Handler returns a rich page DTO; kernel derives a registered provider-safe projection | Handler itself returns one minimized DTO used by page and model | AD-1 demands a shared handler while AD-10 requires minimization, but no canonical result/projection boundary is defined |
| Commands | The model receives proposal-only tools; confirmation endpoint alone can dispatch command keys | Laravel AI exposes command tools using SDK approval pauses, then NEXIAM confirms and resumes them | AD-7 requires confirmation but does not state whether a command is ever model-callable or what component owns post-confirm execution |
| Page packs | Keyed from Inertia component identity, compiled centrally, one exact pack per page | Keyed from Laravel route names, merged from domain fragments at runtime | AD-3 says “canonical page identity” and “one versioned page pack” without defining identity, composition, uniqueness, or collision rules |
| Cross-page skills | Starting a skill creates an immutable task grant that survives page navigation until expiry | Every navigation replaces the pack; missing capability cancels the skill and its proposals | AD-3/AD-5/AD-6 mention page/task grants but never define their creation, authority, or lifecycle |
| Skill engine | Deterministic PHP state machines persist a cursor and allow the model only to fill typed decisions | Declarative YAML supplies tools and limits; the model selects the next step on each turn | Both are versioned, bounded workflows over allowlisted capabilities as required by AD-5 |
| Conversation/run state | Every stream event is stored; run state advances with optimistic concurrency | Only sanitized messages/tool audit are stored; stream deltas are transient and terminal state is last-write-wins | AD-17 requires sanitized event history but does not define event granularity, legal transitions, or concurrency |
| Proposal state | Canonical JSON, SHA-256, one confirmation record, compare-and-swap execution | Database JSON serialization, framework hash helper, multiple decision attempts with the first accepted decision winning | AD-7 names a hash, expiry, idempotency, and binding fields without defining canonicalization or atomic transition rules |
| Streaming | Persisted SSE events with per-run sequence, resumable through `Last-Event-ID` | Queue broadcasts converted to ephemeral SSE with best-effort ordering and a snapshot refetch after reconnect | The readiness envelope lists fields, but neither it nor AD-17 specifies delivery, resume, ordering, or terminal-event semantics |
| UI intents | Server validates and persists intents, then client checks pack/version | Server forwards schema-valid provider output; client alone checks current pack | AD-9 says the server “may emit” a fixed intent and the shell validates it, leaving authoritative validation ownership ambiguous |
| Usage | Monetary micro-unit plus token reservations per institution/user/day in institutional timezone | Ask-count and token reservations per user/month in UTC; cost is analytics only | AD-15 mandates durable budget/reservation but defers units and exact quotas without a common ledger contract |
| RAG | PostgreSQL FTS returns source-span citations and filters inside the query | pgvector returns chunk citations and filters candidates after nearest-neighbor retrieval | AD-12 requires authorization filters and citations but does not define the port result, filter enforcement boundary, or citation support unit |
| Provider adapter | `AiGateway` returns a NEXIAM async event stream and normalized usage/errors | `AiGateway` returns an SDK response/stream wrapper translated later by transport | AD-13 names the port and adapter boundary but supplies no port operations, DTOs, cancellation, errors, or conformance tests |
| Operations | Outbox consumers reconcile reservations/runs, and kill-switch activation cancels uncommitted work | Scheduled polling reconciles usage; kill switch blocks only new turns while in-flight runs continue | AD-15/AD-18 require an emergency stop and recovery but do not define propagation or in-flight semantics |

These units cannot exchange registry definitions, page packs, skill state, proposal hashes, stream consumers, usage records, RAG citations, or provider adapters. Their user-visible behavior also differs on navigation, reconnect, concurrent confirmation, budget exhaustion, kill-switch activation, and command approval. None of those differences clearly violates the current spine.

## Findings requiring AD tightening

- The spine has no normative contract package despite making envelopes and schemas the shared substrate. “JSON Schema-compatible” permits different drafts, unsupported keywords, coercion, defaults, nullability, unknown-field behavior, and error paths. Tighten AD-2 and Consistency Conventions to require one code-owned `Application/Capabilities/Contracts` package containing immutable DTOs, a pinned JSON Schema dialect/subset, strict unknown-field rejection, no implicit coercion/default application at dispatch, stable validation-error paths, canonical serialization fixtures, and build-time rejection of duplicate `(key, version)` registrations. Require registry/page-pack/skill/transport contracts to carry an independent `contract_version` and compatibility policy.

- Authorization has no single enforcement owner or mandatory dispatch order. A kernel that trusts handler decorators and a kernel that performs all checks before a handler both satisfy the prose, but their bypass and audit surfaces differ. Tighten AD-1/AD-2/AD-6 to define one non-bypassable `CapabilityKernel.dispatch(RegisteredInvocation)` pipeline in this order: authenticate current principal → resolve institution/surface/mode/task context → validate schema → authorize application capability → resolve target scope → load/version-check targets → reserve command idempotency → invoke handler → apply caller projection → write audit/outbox → return typed result. Controllers and Nexi adapters may construct only untrusted invocation requests; a server-created execution context is the sole trusted context, and handlers must still enforce domain invariants but must not be the only capability/scope gate.

- Actor, tenant, and invocation provenance are only called “actor reference” and “context,” allowing callers to provide stale or forged authority snapshots. Tighten AD-6/AD-17 with a canonical principal tuple (`actor_type`, opaque `actor_id`, `institution_id`, authenticated session/service identity, surface, correlation ID) resolved fresh by the application, plus an invocation provenance enum (`human_http`, `nexi_read`, `nexi_confirm`, `system_job`). Forbid client/provider-supplied actor, institution, capability, mode, pack, skill, or scope values from entering the trusted execution context; they may only be compared as stale-context hints.

- The shared-handler rule conflicts with model minimization because there is no prescribed boundary between the authoritative result, the page DTO, the tool result, and the provider-visible projection. Tighten AD-1/AD-10 so each capability defines one authoritative typed result and separately registered projections by trusted channel. The kernel, not the controller, orchestrator, or provider adapter, must select and materialize the projection after authorization; provider-visible results must be a dedicated allowlisted projection with classification metadata, while normal UI callers may receive a different registered projection from the same handler. Add contract tests proving prohibited fields cannot appear in tool results, stream events, audit payloads, or provider requests.

- Mutation invocation ownership is ambiguous. One compliant team can expose command tools to the model and rely on Laravel AI approval, while another exposes only proposal tools; that is a material safety and recovery difference. Tighten AD-7 to state that provider-facing tool sets never contain executable `command` capabilities. Orchestration may invoke `read` and `propose`; it persists a proposal that names an executable command. Only the generic application confirmation endpoint, after a human decision and fresh checks, may issue an invocation with provenance `nexi_confirm`. SDK approval is an adapter-level pause signal only and cannot resume an SDK tool closure that commits state. A confirmation retry must return the already-recorded command result rather than ask the model to continue execution.

- Page-pack identity and publication are underspecified. “Canonical matched page identity” could mean route name, Inertia component, URL template, or controller action, and domain-local ownership permits silent duplicate/merge behavior. Tighten AD-3 to define the canonical identity source, a build-time page identity registry, exactly one compiled pack artifact per `(page_identity, pack_version)`, duplicate-key failure, deterministic composition rules if fragments are allowed, and a declared owner. The resolver must return `{page_identity, pack_key, pack_version, context_binding, effective_modes}` as one immutable decision, and unknown pages must fail closed to a named default state rather than inherit the prior pack.

- The relationship between page relevance and a cross-page skill is unresolved. AD-6 refers to a “page/task grant,” but no AD defines a task grant, so navigation can either preserve or revoke the workflow. Tighten AD-3/AD-5/AD-6 to introduce a persisted, server-issued `TaskGrant` with actor, institution, surface, skill/version, allowed capability versions, scope bounds, origin pack/version, creation/expiry, and status. Starting a skill requires the current pack; subsequent steps require the active task grant plus fresh kernel authorization and do not inherit a destination page’s tools. Define navigation, mode demotion, logout, suspension, pack publication, and capability revocation effects on the grant and pending proposals. A page pack is never copied into a conversation as durable authority.

- A “versioned workflow definition” is not enough to make skills interoperable or auditable. The model-directed YAML loop and deterministic state machine above both comply but produce incompatible state and retry behavior. Tighten AD-5 with a canonical skill contract: typed input/output/proposal schemas; finite named states and allowed transitions; which transitions are deterministic versus model-selected; checkpoint persistence; retry/idempotency policy per step; timeout/cancellation/compensation behavior; capability version pins; maximum fan-out; and terminal outcomes. Require the server workflow engine to own the state cursor and validate every transition; prompts may recommend a transition but cannot mutate the cursor directly.

- Conversation, turn, run, tool-call, and proposal aggregates lack legal state machines and ownership relationships. The conceptual tables in the readiness plan explicitly defer exact migrations, so they do not prevent incompatible lifecycles. Tighten AD-17 by defining aggregate ownership (`Conversation` owns ordered `Turn`s; a submitted turn creates at most one active `Run`; runs own tool calls and may create proposals), normative status enums and legal transitions, one-active-run uniqueness, optimistic-concurrency/version columns, and terminal-state immutability. Specify that ownership is checked from the current principal on every read/write and that provider conversation IDs are untrusted adapter metadata, never application identities.

- Proposal binding cannot be reproduced across implementations because “normalized arguments” and “proposal hash” have no canonical form. Tighten AD-7/AD-8 to pin RFC 8785 JSON canonicalization (or another named algorithm), hash algorithm and domain-separation prefix, immutable fields included in the digest, target-version encoding, server-generated idempotency-key derivation, and clock/expiry semantics. Define a single atomic compare-and-swap transition `pending → executing → executed|conflicted|failed`, separate `rejected|expired|cancelled|invalidated` terminal states, a uniqueness constraint on accepted confirmation, and how partial batch results bind to the original proposal. Confirmation must never mutate or re-normalize the proposal being confirmed.

- The stream envelope is illustrative rather than a protocol: every event has `payload: {}` and no semantics for ordering, replay, resume, cancellation, or backpressure. Tighten AD-17 and Consistency Conventions with a versioned discriminated union for every event type, required payload schemas, a unique monotonically increasing sequence per run, at-most-one terminal event, persistence rules, and a resume contract using an event cursor. Define duplicate handling, gap detection/snapshot recovery, retention, heartbeat, client disconnect, queue/provider cancellation, and the exact distinction between “cancel requested,” “generation stopped,” and “domain command already committed.” No provider/SDK delta may bypass this translator.

- UI intent authorization is split between server and browser, and the fixed catalog lacks per-intent schemas and stale-context rules. Tighten AD-9 so only trusted application code—not provider output—constructs the final versioned `UiIntent` union after validating an allowlisted intent request against the current effective pack/task grant. Define route/panel/region registries, parameter schemas, pack/context binding, expiry, deduplication ID, and outcomes. The client must revalidate for defense in depth and ignore stale/unknown intents, but it is not the authority. Clarify that navigation is a UI intent, not a separately executable registry capability, unless a single explicit mapping rule is adopted.

- Usage governance lacks a common accounting unit, period identity, and failure settlement contract, so two ledgers can disagree while both “reserve estimated budget atomically.” Tighten AD-15 with a canonical multi-dimensional ledger: asks, input tokens, output tokens, tool steps, provider-cost micro-units plus currency, and optional latency; institution/user/routing-profile dimensions; policy timezone and reset instants; reservation ID tied uniquely to a run/attempt; maximum hold, expiry, renewal, settlement, release, and unknown-usage states; and database isolation/locking requirements. Define whether rejected, cached, retried, cancelled, and provider-unknown calls consume each dimension, how pricing versions are pinned, and which limit wins when dimensions conflict. Admin overrides must create a new effective-policy version, not rewrite ledger history.

- `AiGateway` is only a name, allowing SDK types, error behavior, and usage semantics to leak through different layers. Tighten AD-13/AD-14 by specifying port methods and NEXIAM-owned request/response/event DTOs for generate, stream, embed if approved, cancel, and health; normalized finish reasons, tool-call representation, structured-output failures, timeout/retry classes, usage precision, provider request ID, and privacy/routing-profile evidence. The port must not expose Laravel AI classes. Require a provider-adapter conformance suite with golden fixtures for stream fragmentation, malformed tools, duplicate tool calls, cancellation, timeout-after-output, missing usage, safety refusal, and unknown provider errors; no adapter is promotable without passing the same suite.

- RAG authorization can occur either inside the database query or after retrieval because “audience/effective-version filters” has no enforcement boundary. Post-filtering nearest-neighbor results can leak through timing, logs, caches, reranking, or insufficient top-k. Tighten AD-12 to require authorization/audience/institution/effective/revocation predicates inside the candidate retrieval operation before any chunk leaves the trusted index adapter. Define `KnowledgeIndexPort` request/response DTOs, filter vocabulary, source/chunk/version IDs, relevance scores, exact cited spans, index snapshot/version, retrieval trace classifications, and stable no-support/refusal reasons. Cite only source versions active in the run’s recorded index snapshot; revocation must make a source ineligible immediately and trigger a defined reindex/deletion workflow.

- Privacy controls reference classifications and pseudonyms without defining a taxonomy, decision owner, or mapping lifetime. Tighten AD-10/AD-11 with a code-owned field-classification catalog, allowed destination matrix keyed by routing profile and purpose, fail-closed treatment of unclassified fields, deterministic redaction/secret-scanner outcomes, and a per-run pseudonym map stored only on the trusted side with explicit retention. Require the firewall to produce a signed/hash-linked `PrivacyDecision` record containing projection version, classifications, transformations, destination profile, and rule version for every provider call, without storing the prohibited raw payload.

- Error categories are too coarse to support compatible HTTP, stream, retry, and UI behavior. Tighten Consistency Conventions to define a versioned error envelope with stable machine code, category, safe message key, correlation ID, retriable flag, retry-after/reset instant where applicable, manual fallback intent, and sanitized details schema. Map every kernel, orchestrator, provider, quota, proposal, and cancellation failure to one code and specify which failures terminate a run, leave a proposal pending, invalidate it, or return an already-committed result.

- Configuration is described by precedence but has no publication/version/cache semantics. Two workers can legitimately resolve different policies during one run. Tighten AD-15/AD-16 so effective policy is an immutable, versioned server decision recorded on every turn/run/reservation; define which checks use the snapshot and which must re-read current emergency, suspension, authorization, provider-health, and budget state. Configuration changes require audited publication, cache invalidation, and monotonic versioning. Explicitly define fail-closed behavior when a policy source is unavailable or internally contradictory.

- Operational ownership is absent for the records and failure states the architecture creates. “Reuse existing patterns” does not identify who reconciles an orphan reservation, stuck run, executing proposal, failed outbox delivery, revoked corpus chunk, or incomplete provider cancellation. Tighten AD-15/AD-17/AD-18 with named durable jobs and owners for reservation settlement, stale-run termination, proposal reconciliation, outbox retry/dead-letter handling, corpus deletion/reindex, retention erasure, and audit verification; define schedules/SLOs, idempotency, alerts, dashboards, and operator-safe replay commands. State precisely that the emergency kill switch is checked before every provider/tool/confirm boundary, blocks new work immediately, prevents uncommitted commands, requests cancellation of in-flight generation, and never reports cancellation of a command already committed.

- The readiness sequence permits OpenSpec 1 to implement “interfaces or minimal persistence required for stubs” before the shared contracts above are fixed, which would make the first implementation’s accidental shapes de facto architecture. Tighten the readiness gates so AI-001 and AI-006 are insufficient by themselves: before foundation coding, approve a contract appendix covering the canonical dispatcher, DTO/schema dialect, identity/context, state machines, stream union, projection boundary, and conformance fixtures. Move exact quota values, provider choice, index technology, and retention duration to their existing ADRs, but do not defer the cross-module shapes and semantics that every later OpenSpec must consume.

## Required disposition

Do not replace the spine with a low-level design. Add one binding **Contract Kernel appendix** and amend the cited ADs so they fix ownership, identity, sequencing, state transitions, and wire compatibility while leaving implementation mechanisms replaceable. Once that appendix exists, Atlas and Beacon may still choose different persistence/SDK/index internals, but they must share observable contracts and become substitutable at the kernel, UI, provider, and operations seams.

## Second-pass findings — AD-20 and AD-21

AD-20/AD-21 correctly reject prompt-owned business rules and ad hoc retrieval. The following remaining holes still allow two compliant teams to make incompatible or unsafe choices.

- “Domain state, Actions/Queries, policies, and deterministic constraint/preflight evaluators own business truth” names several canonical owners without specifying one executable rule path. One team can duplicate capacity/eligibility logic in an Action and a preflight; another can make the Action call the evaluator. Both comply, but only the latter structurally prevents drift. Tighten AD-20 so each business predicate has one code-owned domain rule/evaluator invoked by preview preflight and again inside the authoritative command transaction under the command’s locks. The Action may add commit-only invariants, but may not reimplement a registered preflight predicate. Require conformance tests that run the same normalized cases through preview and command execution and compare stable rule codes.

- The confirmation preflight is described as the “same preflight” without distinguishing the proposal-time rule version from the currently active rule version. A team can reload the old evaluator to reproduce evidence while another uses the new evaluator to enforce current policy. Tighten AD-20 so proposal display may reproduce the recorded evidence, but confirmation must resolve the currently active `RuleSetRef`, compare it with every proposal dependency, execute the current evaluator, and invalidate before command dispatch when any non-compatible dependency changed. Historical evaluator code is never loaded merely to make an old proposal executable.

- `RuleSetRef` is singular on each mutation capability even though a schedule proposal can depend on eligibility, capacity, overlap, lifecycle, calendar, and institution policy rule sets. A single aggregate digest can hide which dependency changed; separate teams can calculate it differently. Tighten AD-20 to use a canonical ordered `RuleDependencySet` of `(rule_key, rule_version, digest, compatibility_class)` entries plus one set digest computed with the Contract Kernel’s canonicalization rules. Persist the exact dependency set on the preflight evidence, proposal, task grant, prompt digest, and audit event.

- AD-7’s proposal digest binds actor, institution, command/version, normalized arguments, target versions, impact, expiry, and idempotency identity, but AD-20 does not amend that binding to include `RuleSetRef`/rule dependencies or `ConstraintEvidence`. A proposal’s evidence can therefore be replaced or mismatched without necessarily changing the confirmation hash. Tighten AD-7/AD-20 so canonical proposal bytes include the rule-dependency-set digest, preflight identity/version, complete canonical `ConstraintEvidence` digest, projection/privacy version used for the impact summary, and evidence observation time. Confirmation must verify those bindings before the compare-and-swap transition.

- “Pass or explicit confirmable result” leaves the override boundary undefined. One team can treat a capacity breach as confirmable with a warning; another can treat only preference conflicts as confirmable. Tighten AD-20 with code-owned evidence outcomes such as `pass`, `confirmable_warning`, `hard_fail`, and `indeterminate`, stable rule codes, and a registry-owned list of which warning codes are confirmable for each capability. Only domain policy may mark a rule confirmable; model text, prompt configuration, ordinary admin configuration, or the user’s confirmation cannot downgrade a `hard_fail` or `indeterminate` result.

- `ConstraintEvidence` is called typed but its minimum semantics are absent. Teams can disagree about whether evidence proves scope, target freshness, each rule result, or merely a top-level boolean. Tighten the Contract Kernel/AD-20 with a versioned evidence union containing preflight key/version, normalized-argument digest, target snapshot/version digest, rule dependency set, ordered per-rule code/outcome/safe facts, assumptions, observed-at instant, actor/scope decision reference, overall outcome, expiry, and evidence digest. Evidence must be deterministic for the same authorized snapshot except for declared observation metadata.

- Proposal preflight and command execution still have a time-of-check/time-of-use gap unless the command transaction rechecks the same rules under authoritative locks. Target versions reduce but do not eliminate this for aggregate/cardinality constraints such as total capacity or cross-session overlap. Tighten AD-20 so confirmation preflight is advisory until the Action repeats all commit-relevant rules inside its transaction after acquiring the domain-defined locks. A post-confirm rule conflict must produce a typed non-commit outcome tied to the proposal and may never be converted to partial success unless AD-8 declared partial semantics.

- Rule change propagation is a sequence of rebuild instructions, not an atomic publication contract. During rollout, workers can observe a new domain evaluator with an old registry descriptor, pack, skill, or prompt digest. Tighten AD-20 with an immutable `RulePublication` bundle/version that references compatible registry, page-pack, skill, prompt, and evaluator artifact digests; publish it atomically through a monotonic active pointer. Runs record the publication version, while every tool/confirm boundary compares current safety-critical rule state. Mixed or unavailable bundles fail closed for proposal creation and confirmation.

- “Invalidates incompatible proposals/task grants” has no dependency index or reliable propagation mechanism. A deployment can publish a new rule yet leave existing records active until touched. Tighten AD-20/AD-18 to require a rule-publication outbox event and indexed reverse dependencies from rule keys/versions to proposals, task grants, context epochs, cached descriptors, and evaluations. The event consumer invalidates affected durable state idempotently; the kernel independently rejects stale dependencies on use so delayed event processing cannot preserve authority. Define observability and reconciliation for incomplete invalidation.

- “Capability/version changes are required only when contract or semantics change” is circular because a business-rule change normally changes observable acceptance semantics. Teams can either bump every capability or none. Tighten AD-20 with an explicit compatibility policy: rule-only changes always bump the rule dependency version; capability version bumps only for input/output/projection/handler contract incompatibility; `contract_version` follows the Contract Kernel compatibility rules. Proposal executability is decided by rule dependency compatibility, never inferred from an unchanged capability key.

- AD-21 declares one source registry but does not define its identity, representation, or enforcement API. One team can build a database catalog for documents only while another builds a code registry covering Query capabilities. Tighten AD-21 to define a versioned `KnowledgeSourceDefinition` contract with stable source-class key/version, owner/approver authority, institution/audience/purpose policy, data classification, lifecycle state machine, and exactly one registered retrieval-route reference (`KnowledgeIndexPort` collection/profile or Capability Registry read key/projection). Duplicate or missing definitions fail build/publication; source instances reference one definition version.

- The source registry currently “declares” a retrieval route but no rule forces the orchestrator to consult it before retrieval. Existing deterministic Queries or a future index adapter can be called directly and still claim their sources were classified. Tighten AD-21 so all provider-bound knowledge acquisition enters one `KnowledgeRouter.resolve(request, trusted_context)` seam. It resolves the active source definition, performs purpose/audience/institution checks, issues the protected-read invocation grant, and dispatches only the registered index/query route. `KnowledgeIndexPort` and operational Query results cannot enter provider context without a router decision/evidence ID enforced by the prompt/data firewall.

- The term “every information path” is overbroad enough to imply ordinary human page reads must traverse the knowledge registry, yet the stated design appears intended for AI/provider-bound knowledge. Teams can therefore either wrap the whole application or leave assistant Query paths outside the registry. Tighten AD-21’s scope: the registry governs every AI/provider-bound retrieval, corpus ingestion/publication, and citation path; ordinary UI reads remain on the Capability Kernel path, but any result later projected into an AI run must receive a KnowledgeRouter decision before egress.

- Knowledge-source lifecycle fields do not form a legal publication state machine. A source can be effective but only partly extracted/indexed, or revoked in the registry while stale chunks remain retrievable. Tighten AD-21 with canonical states and transitions such as `draft → approved → indexing → active`, plus terminal/superseded/revoked/deletion-pending states. Only an approved, effective, fully indexed source version may become active; publication atomically advances an index snapshot. Revocation immediately denies retrieval at the registry predicate, invalidates caches/context citations, emits deletion/reindex work, and remains denied even while physical deletion is pending.

- Source approval metadata is not bound to application authorization. An arbitrary importer could potentially assign owner/approver fields without proving that the actor had corpus-publication authority. Tighten AD-16/AD-21 so create, approve, publish, supersede, revoke, and delete are distinct typed Capability Kernel commands with separation-of-duty policy where required, immutable decision evidence, idempotency, and outbox events. Registry rows are not authoritative merely because they contain an approver identifier.

- Dual-use material is not resolved. The same institutional terms may exist as a published policy document and as text copied into an operational record; the current class-to-route wording does not say whether multi-class sources are prohibited or how precedence works. Tighten AD-21 so each source instance has one immutable primary class and route per version; derived/copied material must retain provenance to the approved source or remain operational and ineligible for indexing. Classification conflict fails closed and requires a newly approved version rather than runtime route guessing.

## Second-pass required disposition

Keep AD-20/AD-21, but amend them before approving AI-009. The minimum closure is: one reusable rule evaluator path invoked by both preflight and transactional Action; a canonical multi-rule evidence contract bound into the proposal hash; an atomic rule-publication/dependency-invalidation mechanism; and a versioned knowledge-source definition enforced through one `KnowledgeRouter` before any provider-bound retrieval. Those changes preserve the lean architecture while preventing independent domain, AI, and corpus teams from rebuilding authority at their seams.

## Closure review

The preceding second-pass findings are retained as historical review evidence. The current spine closes their high/critical integration consequences:

- AD-20 now requires preview preflight and the authoritative Action/queue worker to invoke the same domain-owned evaluator path, with domain-defined locks and a typed non-commit result on final conflict.
- AD-7 and AD-20 now bind the canonical ordered `RuleDependencySet`, preflight identity, complete `ConstraintEvidence` digest, projection/privacy version, and observation time into RFC 8785 proposal bytes; evidence has explicit `pass`, `confirmable_warning`, `hard_fail`, and `indeterminate` outcomes that prompts/users/admins cannot downgrade.
- AD-22 now publishes one immutable artifact bundle through a monotonic atomic pointer, records publication versions on runs, maintains indexed reverse dependencies, emits idempotent invalidation work, requires independent kernel rejection of stale dependencies, and reconciles incomplete propagation before authority can be reused.
- AD-21 now defines a versioned `KnowledgeSourceDefinition`, exactly one registered retrieval route, fail-closed source lifecycle, and mandatory `KnowledgeRouter.resolve(...)` enforcement with a decision/evidence ID required by the Prompt/Data Firewall for every AI/provider-bound retrieval.
- AD-16 binds knowledge lifecycle changes to distinct authorized, audited, idempotent Capability Kernel commands rather than treating owner/approver fields as authority.

**Closure verdict:** **PASS.** Independent teams may choose different persistence, index, and worker implementations only behind the same evaluator, proposal, publication, and knowledge-routing contracts; they can no longer produce the previously identified incompatible authority paths while claiming compliance.
