# AI Assistant Foundation Architecture Memlog

- `scope` — Nexi universal Inquiry and Assistant capability across authenticated NEXIAM surfaces.
- `purpose` — Converge implementation units on one safe, scalable application/AI boundary and provide the founder/developer readiness sequence.
- `altitude` — Feature architecture governing later foundation, Inquiry/RAG, and page-assistant OpenSpecs.
- `constraint` — Existing GF-03/GF-06/GF-08/GF-10/GF-20–GF-23 and the master roadmap remain binding; AI is assistance and ordinary application commands remain authoritative.
- `event` — 2026-08-10: exam-session-scheduling archived PASS; active OpenSpec `ai-assistant-foundation` drafted for OpenSpec 1 only (degraded shell + SurfaceProfile/PageCapabilityPack + NexiSessionView). Provider/RAG/kernel/mutations remain later OpenSpecs.
- `constraint` — The target runtime is the existing Laravel 13 modular monolith in `system/`; legacy is evidence only.
- `constraint` — Current Nexi wrap-island chrome, Assistant/Inquiry surface, degraded state, and typed-action preview seam are retained and hardened rather than replaced.
- `decision` — Adopt a hexagonal modular-monolith design with a shared Capability Kernel; browser controllers and Nexi are peer inbound adapters over the same application commands and queries. Binds all application interactions and prevents duplicate AI routes/business logic.
- `decision` — Expose only a small conversation transport API for Nexi; never create one AI route per application route and never give the model arbitrary URL, HTTP, controller, database, filesystem, web-fetch, or code-execution access.
- `decision` — Define every callable operation once in a versioned Capability Registry with stable key, kind, typed schema, capability, scope resolver, risk, confirmation policy, idempotency policy, result schema, and handler. The registry delegates to existing/new domain Actions and Queries.
- `decision` — Require normal page controllers to dispatch through the same Capability Kernel as Nexi when a capability is AI-exposable; route middleware remains defense in depth, not the sole authorization boundary.
- `decision` — Resolve a server-authored Page Capability Pack on every page transition. A pack selects allowed modes, projections, capability keys, navigation targets, disclosure, and privacy class; it is a curated view of the global registry, not a duplicated route list or authorization grant.
- `decision` — Inquiry has no mutation tools and uses only approved policy retrieval plus deterministic authorized own-data queries. Assistant adds page/task tools and skills only when the effective policy and page pack allow them.
- `decision` — Inquiry-to-Assistant is a privilege escalation requiring explicit user confirmation outside model text. Assistant-to-Inquiry and forced demotion on an inquiry-only page are safe with a visible notice. Countdown text is never consent.
- `decision` — Skills are versioned server-side workflow definitions that compose registered capabilities. They may plan and run bounded read steps; mutations resolve to a persisted proposal and ordinary command/batch command after confirmation. Administrators cannot register arbitrary prompts, tools, classes, routes, or URLs.
- `decision` — Multi-step orchestration is bounded by server-owned step, time, token, cost, retry, and tool-chain limits. Every step re-resolves actor, mode, capability, scope, state, and budget; model plans never become authority.
- `decision` — Every assistant mutation uses preview → persisted proposal → explicit confirmation → reauthorization/revalidation → execute. Confirmation binds actor, capability, exact normalized arguments, target versions, impact summary, expiry, and proposal hash; any drift invalidates it.
- `decision` — Bulk work uses purpose-built batch commands or queued operations with an exact impact set and partial/atomic semantics, not repeated hidden POST requests or page hopping.
- `decision` — Nexi sends declarative UI intents (navigate, refresh, focus, open panel, show proposal, show citation) and authoritative result events; the client validates them against the server page pack and never accepts model-authored DOM selectors or component paths.
- `decision` — Authorization and retrieval occur before prompt construction. Context comes only from field-allowlisted projections; operational records are not embedded for RAG, and pseudonymous references replace direct identifiers whenever the task does not require identity.
- `decision` — Treat prompts, retrieved documents, provider output, and tool output as untrusted data. A deterministic Prompt/Data Firewall performs classification, minimization, schema validation, output escaping, link allowlisting, secret/PII checks, and audit metadata; no sanitizer library or system prompt is an authorization control.
- `decision` — Keep policy-document RAG separate from own-data/task queries. Policy RAG requires approved/versioned corpus chunks and citations; own-data and staff operations use authorized application projections rather than embeddings.
- `decision` — Put provider access behind a NEXIAM `AiGateway`. Adopt the first-party `laravel/ai` SDK as the recommended adapter implementation after its ADR/OpenSpec, pinning a reviewed 0.10.x release in the lockfile; no domain or capability code imports provider-specific APIs.
- `decision` — Use Laravel AI structured output, bounded tool loops, streaming, fakes, and approval events as transport conveniences only. NEXIAM owns conversation authorization, proposals, confirmation evidence, privacy, usage settlement, audit, and recovery.
- `decision` — Pin provider and model versions in a centrally approved routing profile. Do not use dynamic cheapest/smartest selection or cross-provider failover until every provider has equivalent approved privacy, retention, region, cost, and evaluation evidence.
- `decision` — Resolve availability in strict precedence: emergency environment kill switch → institutional policy → actor capability/scope → per-user suspension/override → page pack → provider health → durable budget/rate state. Return one typed effective state to UI and executor.
- `decision` — Separate burst throttling from durable budgets. Use Laravel rate limiting for short-window abuse control and an authoritative usage ledger/reservation/settlement flow for per-user and institutional ask/token/cost limits, including concurrent requests and provider failures.
- `decision` — Administrators may control approved availability, quotas, model routing profiles, corpus publication, and emergency suspension through typed audited commands; they may not edit raw production prompts or register arbitrary tools.
- `decision` — Persist conversations, runs, tool calls, proposals, confirmations, citations, usage, and sanitized failure metadata under explicit ownership and retention. Raw chain-of-thought is never requested or stored; sensitive prompt/tool payloads are minimized or separately protected.
- `decision` — Provider outage, quota exhaustion, policy disablement, or failed evaluation produces an explicit degraded state and manual page path. Manual scheduling and all authoritative workflows remain complete.
- `decision` — The universal Nexi dock stays mounted in the authenticated shell, while server policy chooses hidden, Inquiry-only, Assistant-enabled, degraded, or suspended state per page and actor. Conversation survives navigation; tool availability is recomputed and stale proposals are invalidated.
- `decision` — Begin with an exam-session vertical slice: schedule inquiry/read projections, conflict analysis, and a small set of proposal-only scheduling capabilities; do not begin with unrestricted global tools or RAG plus actions in one release.
- `direction` — Use a self-managed `KnowledgeIndexPort` and benchmark PostgreSQL full-text versus a locally operated pgvector hybrid before selecting a RAG store; provider-hosted vector stores are not the default because authorization, revocation, backup, and retention must stay application-owned.

- `decision` — Domain state, Actions/Queries, domain policies, and deterministic constraint/preflight evaluators are the single authority for business rules and proposal validity. Prompts, skills, registry descriptions, and model output are projections or candidates and never duplicate or replace those rules.
- `decision` — Every proposal-capable mutation binds a versioned `RuleSetRef` and target snapshots, runs the canonical domain preflight before persistence, records typed `ConstraintEvidence`, and runs the same preflight again at confirmation. Invalid or stale candidates cannot become executable proposals.
- `decision` — A business-rule change updates the domain rule/action and its tests first; the code-owned registry references the new rule-set version, generated rule digest/tool descriptors/page packs/skills rebuild, affected context epochs segment, and incompatible pending proposals/task grants invalidate. Capability version changes occur only when the capability contract or semantics change.
- `decision` — System prompts receive a generated, versioned rule digest and skill guidance to improve model decisions, but authorization and validity stay in the kernel/domain preflight. Administrators cannot edit prompt text to change business rules.
- `decision` — Use one NEXIAM-owned knowledge-source registry and retrieval facade. Approved institutional policy documents (including published terms/conditions) use versioned/cited RAG; own-data and operational records use authorized deterministic Queries. No ad hoc embeddings or alternate retrieval paths are permitted.
- `version` — Standards baseline researched 2026-08-09: JSON Schema Draft 2020-12 for contracts, RFC 8785 JCS for proposal canonicalization, OWASP LLM/agentic guidance for prompt injection and excessive agency, NIST AI RMF Generative AI Profile for lifecycle risk evidence, Laravel AI SDK as an adapter candidate, and MCP only as a contract/authorization reference rather than NEXIAM authority.
- `decision` — Proposal integrity is a versioned contract: ordered `RuleDependencySet` entries and digest, preflight identity, canonical `ConstraintEvidence` digest, projection/privacy version, and observation time are included in proposal bytes and verified at confirmation and queued commit. Evidence outcomes are `pass`, `confirmable_warning`, `hard_fail`, or `indeterminate`; only domain-registered warnings may be confirmable.
- `decision` — Proposal preview and final command execution invoke one domain-owned evaluator path. The final transaction/worker acquires domain locks, resolves the active `RulePublication`, reruns all commit-relevant checks, and returns a typed non-commit conflict on drift.
- `decision` — `RulePublication` is an immutable atomic bundle of evaluator/registry/page-pack/skill/PromptSpec digests with reverse dependencies and an idempotent invalidation outbox; the kernel rejects stale deps even if consumers lag, and reconciliation repairs incomplete invalidation.
- `decision` — `KnowledgeSourceDefinition` is a versioned contract with one primary class and retrieval route. All provider-bound retrieval crosses `KnowledgeRouter`, which returns source decision evidence required by the Prompt/Data Firewall; source revocation invalidates caches, epochs, in-flight/replayable citations, and answer artifacts before async deletion/reindex.
